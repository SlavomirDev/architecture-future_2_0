## Ключевое архитектурное решение: замена ESB на Kafka
В текущей системе **ESB** выполнял не только маршрутизацию, но и:
- бизнес-логику (ФЛК, валидации);
- трансформации данных;
- orchestration сервисов;
- адаптеры протоколов.

### Как распределяется логика ESB по целевой архитектуре (C4)

| Функция в ESB | Куда перемещается |
|---------------|-------------------|
| **Маршрутизация запросов (HTTP → сервис)** | API Gateway |
| **Протокольные адаптеры (SOAP, FTP, JMS)** | API Gateway + сервисы |
| **Валидация входных данных (ФЛК)** | Входной слой сервисов |
| **Бизнес-правила (например, скоринг)** | Внутри доменов или Semantic Layer |
| **Трансформация сообщений (XML→JSON, map)** | В сервисах-продюсерах / консьюмерах |
| **Orchestration нескольких сервисов** | Choreography через Kafka + Saga |
| **Маршрутизация на основе контента** | Kafka + Stream Processing (KSQL / Flink) |
| **Dead Letter Queue, retry** | Нативные механизмы Kafka + мониторинг |
| **Логирование вызовов** | Service Mesh / Observability |

# Итог: ключевые проблемы для бизнеса
1. Самая болезненная точка — это текущий DWH. Он перегружен, в нём слишком много логики, и из-за этого отчёты строятся слишком долго. Это напрямую влияет на скорость принятия решений.
2. Вторая проблема — отсутствие разделения на домены. Сейчас всё связано между собой, поэтому любые изменения даются дорого и долго. Это мешает развивать финтех, медицину и новые направления отдельно.
3. Также заметна сильная зависимость через интеграционную шину. Это усложняет подключение новых партнёров и в будущем будет тормозить рост экосистемы.

# Приоритет действий
В первую очередь нужно:
- разделить систему на домены (медицина, финтех, AI);
- разгрузить DWH и вынести из него бизнес-логику;
- заменить ESB на Kafka, вынеся всю логику в API Gateway, доменные сервисы и слой обработки данных;
- перейти к потоковой передаче данных вместо жёстких интеграций.

Далее имеет смысл:
- построить полноценную платформу данных (Raw → Domain DWH → Semantic Layer);
- навести порядок в управлении данными (доступы, каталог, происхождение);
- упростить доступ к данным через единые API.

И уже после этого можно:
- развивать инфраструктуру для моделей (Feature Store, ML-сервисы);
- добавлять обработку данных в реальном времени в полном объёме.

# Вывод
Если упростить: данные, логика и интеграции завязаны в одном месте, и это мешает компании расти.  
Чтобы двигаться дальше, нужно разделить систему на части, упростить связи между ними и сделать работу с данными более прозрачной. Это даст более быстрые отчёты, упростит развитие новых направлений и позволит подключать новые бизнесы без сильной переделки всей системы.
