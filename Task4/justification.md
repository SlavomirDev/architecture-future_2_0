# Обоснование конфигурации Terraform для Hadoop-кластера

## 1. Выбор ресурсов и их параметров

### 1.1 Виртуальные машины (2 CPU, 4 GB RAM)

**Параметры:**
- `cores = 2` — два виртуальных ядра на узел
- `memory = 4` — 4 гигабайта оперативной памяти

**Обоснование:**
- Для тестового Hadoop-кластера 2 CPU и 4 GB RAM являются минимально достаточной конфигурацией
- Этого объёма ресурсов достаточно для запуска основных компонентов Hadoop:
  - NameNode (управление метаданными HDFS)
  - DataNode (хранение данных)
  - ResourceManager (управление ресурсами)
  - NodeManager (выполнение задач)
- При необходимости параметры легко масштабируются через переменные `cores_per_node` и `memory_per_node`
- Такая конфигурация обеспечивает баланс между производительностью и стоимостью облачных ресурсов

### 1.2 Диски (20 GB, network-ssd)

**Параметры:**
- `size = 20` — 20 гигабайт дискового пространства
- `type = "network-ssd"` — сетевой SSD-диск

**Обоснование:**
- 20 ГБ достаточно для установки операционной системы, Java Runtime Environment и базовых компонентов Hadoop
- SSD-диски обеспечивают высокую скорость ввода-вывода, критически важную для:
  - Быстрой загрузки операционной системы
  - Эффективной работы HDFS (Hadoop Distributed File System)
  - Ускорения обработки данных при выполнении MapReduce задач
- Тип `network-ssd` выбран как оптимальный по соотношению цена/производительность для аналитических нагрузок

### 1.3 Сеть и подсеть (10.0.0.0/24)

**Параметры:**
- CIDR блок: `10.0.0.0/24` (256 доступных адресов)
- Включен NAT (`nat = true`) для каждой ВМ

**Обоснование:**
- Приватная сеть 10.0.0.0/24 обеспечивает:
  - Изоляцию внутреннего трафика Hadoop-кластера
  - Достаточное количество IP-адресов для масштабирования до 256 узлов
  - Безопасность за счёт отсутствия прямого доступа из интернета
- Включение NAT необходимо для:
  - Скачивания пакетов через `apt` при установке ПО
  - Обновления системы и компонентов
  - Удалённого доступа по SSH для администрирования кластера
  - Возможности интеграции с внешними сервисами

### 1.4 Образ операционной системы (Ubuntu 22.04 LTS)

**Обоснование:**
- Ubuntu 22.04 LTS — стабильный и поддерживаемый дистрибутив
- Широкая документация и сообщество
- Поддержка до 2027 года (Long Term Support)
- Совместимость с Hadoop и необходимыми зависимостями
- Простота автоматизации через cloud-init и метаданные

### 1.5 SSH-ключи для доступа

**Обоснование:**
- Использование SSH-ключей вместо паролей повышает безопасность
- Автоматическая передача публичного ключа через метаданные упрощает развёртывание
- Позволяет выполнять дальнейшую настройку кластера через Ansible или другие инструменты

## 2. Причины использования декларативного подхода (Infrastructure as Code)

### 2.1 Воспроизводимость
- Одна и та же конфигурация Terraform создаёт идентичную инфраструктуру в любой момент времени
- Исключаются человеческие ошибки, возникающие при ручном создании ресурсов
- Возможность быстрого развёртывания dev/staging/prod окружений

### 2.2 Версионирование
- Все конфигурации хранятся в Git, что позволяет:
  - Отслеживать изменения инфраструктуры во времени
  - Возвращаться к предыдущим версиям при необходимости
  - Проводить код-ревью изменений инфраструктуры

### 2.3 Масштабируемость
- Изменение переменной `node_count` автоматически создаёт нужное количество ВМ
- Легко адаптировать параметры ресурсов под разные нагрузки
- Консистентная конфигурация всех узлов кластера

### 2.4 Документация как код
- Конфигурация Terraform служит документацией инфраструктуры
- Новые члены команды быстро понимают архитектуру и взаимосвязи ресурсов
- Нет необходимости в отдельной документации, которая быстро устаревает

### 2.5 Управление жизненным циклом
- Простое удаление всей инфраструктуры через `terraform destroy`
- Экономия средств за счёт быстрого освобождения неиспользуемых ресурсов
- Возможность безопасного экспериментирования с конфигурациями

## 3. Соответствие бизнес-требованиям компании «Будущее 2.0»

### 3.1 Ускорение time-to-market
- Развёртывание Hadoop-инфраструктуры занимает менее 5 минут вместо нескольких часов ручной настройки
- Быстрое создание изолированных сред для разных бизнес-доменов (медицина, финтех, ИИ-сервисы)
- Сокращение времени на подготовку инфраструктуры под новые направления

### 3.2 Гибкость и масштабируемость
- Параметризация позволяет использовать один код для разных типов окружений
- Легкое масштабирование кластера при росте объёмов данных
- Возможность быстрого подключения новых бизнес-направлений через создание отдельных сетей и ВМ

### 3.3 Безопасность и соответствие регуляторам
- Изоляция критичных данных в приватных подсетях
- Контролируемый доступ через SSH-ключи
- Единые политики безопасности для всех ресурсов
- Отсутствие медицинских карт и историй болезней в аналитической витрине (вынесены в отдельные домены)

### 3.4 Экономическая эффективность
- Оптимальный выбор ресурсов для начального этапа
- Возможность быстрого удаления неиспользуемых ресурсов
- Гибкое масштабирование без переплаты за неиспользуемые мощности
